1. OBJECTIVE AND CONFIRMED DIRECTION

Replace metadata learning from historical examples with AI-proposed, user-approved,
versioned lessons. Generation receives the selected clip's evidence and applicable
approved guidance. Other clips' metadata must never enter that request.

Confirmed by the user:
- Remove the existing metadata learning mechanics that reuse old clip metadata.
- Analyse successful clips and derive lessons rather than injecting donor examples.
- Plan the replacement and removal together.

Execution baseline, authorized by the request to execute this plan:
- Exclude old titles, descriptions, tags and generated variants from BOTH lesson
  analysis and metadata generation. Analyse clip content plus performance instead.
- Replace metadata adaptive feedback guidance too. Approval/rejection remains review
  history; it cannot silently influence generation outside approved lessons.
- Keep unrelated clip-discovery learning unchanged in this bounded increment.
- Begin with manually triggered analysis and explicit lesson approval, no schedule.
- Retain historical metadata for publishing, history and audit; remove its learning
  access paths rather than deleting legitimate saved packages or source videos.

3. TARGET FLOW AND INFORMATION BOUNDARY

Owned-channel performance records + linked local clips/transcripts
 -> deterministic eligibility and comparison cohorts
 -> bounded content evidence extraction
 -> AI lesson proposals with evidence and limitations
 -> review diff / edit / approve / reject
 -> immutable approved lesson versions
 -> applicable guidance + selected clip evidence
 -> metadata generation -> grounding validation -> candidate review

The analyst and generator must use separate typed input builders, not whole
database records with fields removed later. Analyst allowlist: opaque clip IDs,
duration, transcript/segment evidence, optional supported frame observations,
explicit content category, publish age and numeric performance snapshots.
No old display names, titles, descriptions, hashtags, tags, variants, free-form
feedback or metadata-bearing analytics summaries. Use structured measurements
from performance services, not prose coaching responses containing old metadata.
Never infer a category from historical titles. Unclassified clips can be reviewed
manually or grouped using content-only evidence.

The generator has no historical-example repository dependency. Lesson evidence
IDs may be recorded for audit but must not trigger donor-record hydration.

4. DELIVERY PHASE A: REMOVE LEGACY METADATA LEARNING FIRST

Ship as an independently usable change before adding the analyst:
- Delete metadata example selectors/formatters, prompt sections and LearningContext
  plumbing. Remove raw approved/rejected/high-performing example retrieval.
- Stop metadata from consuming buildAdaptiveGuidance and legacy knowledge-entry
  text. Existing entries are legacy, inactive for metadata, available for review.
  Do not automatically promote them to approved lessons.
- Replace metadata settings with lessons disabled/enabled. Until lessons exist,
  generation uses the current clip and reviewed profile editorial instructions.
- Remove example-count bonuses from metadata scoring and recommendation selection;
  preserve the remaining formula and document the resulting score change. Do not
  replace them with a lesson-count bonus or silently retune other weights.
- Audit all generation entry points: all sections, individual sections, coach
  handoff, retry, append and heuristic fallback. All use the same clean builder.
- Saved worker prompts can themselves contain old clip facts. Inventory and flag
  those instructions for review, show proposed edits, and keep reviewed editorial
  preferences. Do not silently rewrite custom prompts or claim the boundary is
  complete while unreviewed legacy learning instructions still enter requests.
- Keep the current draft separate from source evidence. A previously generated
  draft must not establish an event or speaker fact. Validate continuity hints
  against selected-clip evidence; support clean regeneration without those hints.
- Existing variants are not repaired automatically. Mark legacy generations as
  predating this change, offer regeneration, and apply grounding validation before
  recommending or reusing them. Preserve scheduled/published packages.

Phase A acceptance: unique donor facts in any legacy store never appear in any
metadata request, even when all old learning switches were enabled. Generation
works without lessons, and scores do not depend on historical example counts.

5. DELIVERY PHASE B: LESSON STORAGE AND REVIEW

Add dedicated lesson, lesson-version, analysis-run and decision/audit records to
existing JSON persistence; use additive, idempotent normalization and backup before
migration. No new database engine, vector store or multi-agent framework needed.

Each lesson version contains:
- Stable lesson ID, immutable version ID, task/profile scope and applicable kinds.
- General guidance, applicability, exceptions and observation vs hypothesis label.
- Confidence explanation, sample size, cohort/metric definitions and evidence IDs.
- Source content/performance timestamps, analysis model and prompt version.
- Proposed/approved/rejected/superseded/retired status and decision timestamps.

Editing an approved lesson creates a proposal; its approved predecessor remains
active until replacement approval. Retirement requires an explicit decision.
Approval cannot change worker prompts, model assignments or scoring weights.

UI: a compact Metadata Lessons area reachable from Performance and metadata AI
profile settings. Show active lessons, proposals, evidence, limitations and version
diff. Controls: analyse, edit proposal, approve, reject, retire and inspect history.
Selecting no active lessons remains a supported mode. Scope defaults to the
originating profile; cross-profile sharing requires an explicit user action.

6. DELIVERY PHASE C: PERFORMANCE AND CONTENT ANALYST

Use a bounded app-owned local AI task with an explicit assignment/configuration;
do not silently repurpose the current metadata worker or change assignments.
Reuse the action executor, job lifecycle, cancellation and local-AI scheduler.

- Start from owned-channel measurements and explicit local clip/video linkage.
  Exclude unlinked videos rather than guessing identity from a title.
- Show eligible/excluded counts and reasons before running. Bound batch size,
  content length, frame count and runtime; checkpoint work and support cancellation.
- Compare similar duration, publish-age and content cohorts. Include a comparable
  ordinary-performing baseline to avoid learning only from winners.
- Treat unavailable metrics as missing, never zero; show stale data and distinguish
  organic observations from causal claims. Do not invent CTR or retention curves.
- Derive content features from transcripts first: hook timing, setup, payoff,
  surprise and supported speaker/action evidence. Label visual claims unavailable
  unless frames/video were actually inspected by a supported vision path.
- Use multiple independent clips to support broad proposals. A single-clip finding
  remains a weak observation. If data are insufficient, return no proposal with a
  clear reason; never fill a quota by inventing lessons.
- Require evidence references for each proposed rule. Prohibit event-specific
  names, quotes and donor narratives in executable lesson guidance.
- Detect overlap/conflicts with active lessons. Propose a revision/retirement with
  supporting evidence, never overwrite an approved version automatically.
- Treat transcripts and source text as untrusted evidence, not instructions.

Limitation: excluding historical metadata prevents estimating its effectiveness.
V1 lessons describe content/performance patterns and packaging hypotheses. Future
prospective experiments can evaluate those hypotheses under a separately agreed
design; do not claim that high views prove a title formula works.

7. DELIVERY PHASE D: APPLY LESSONS AND VALIDATE OUTPUT

- Select only active approved lesson versions for the current profile/task, requested
  metadata kinds and evidence-supported applicability. Start with deterministic
  filtering and a bounded prompt budget, not semantic retrieval of old clips.
- Snapshot versions when a request begins. Record current clip/transcript identity,
  lesson versions, generation model and grounding result. Later lesson edits cannot
  alter that historical manifest.
- Pass only guidance/applicability/exception fields to generation, never evidence
  excerpts, donor titles, evidence narratives or raw performance records.
- Validate structured output and compare factual claims to selected-clip evidence.
  Use deterministic identity/speaker checks plus a separate bounded grounding pass
  where needed. A model verifier reduces risk; it does not guarantee truth.
- Classify unsupported/uncertain claims. Retry once with corrective evidence; if
  still unresolved, withhold the candidate with a useful reason. Do not accept
  schema-valid factual contamination or silently switch to invented fallback facts.
- Sparse transcripts may not describe visual action. Let the user review a factual
  clip note or supply supported visual evidence rather than borrowing a narrative.
- Reject stale results when clip selection or evidence changes during generation.

10. EXECUTION DECISIONS

- Strict exclusion applies to both analyst and generator.
- Metadata-only replacement; discovery feedback remains scoped and unchanged.
- Preview exposes configurable defaults of two days and twenty measured views,
  with four distinct comparable videos per cohort and snapshots at most 14 days old.
  These are starting filters, not evidence of statistical significance.
- V1 is transcript-only. Vision inspection is not claimed or implemented here.
- Executable lessons use a controlled strategy vocabulary. AI observations and
  supporting quotes remain review-only; users edit strategy, scope and sections.
- YouTube-library generation requires a unique local clip/channel link and cannot
  substitute old remote metadata when source evidence is absent.
- No general store/lesson import UI exists; new import functionality is outside
  this change. Legacy configuration cannot reactivate deleted learning paths.
